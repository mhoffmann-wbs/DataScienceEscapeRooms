# Build plan

A browser-based, gather.town-style escape room game for data science students. Players walk around a 2D lobby, chat and talk with people nearby, form teams at doors, and solve themed data science puzzles together. It runs as a static site on GitHub Pages with no backend and no third-party accounts.

Architecture details live in [CLAUDE.md](../CLAUDE.md). This file tracks *what* gets built and in which order.

## Decisions

| Topic | Decision |
|---|---|
| Hosting | Static site on GitHub Pages (`/DataScienceEscapeRooms/`), deployed by GitHub Actions |
| Stack | Vite, TypeScript, React overlays, Phaser 4 world, Tiled maps |
| Networking | Peer-to-peer via Trystero over public, account-free relays, behind a swappable `Transport` interface |
| Communication | Text chat (lobby and per team room) and proximity voice/video |
| Identity | Nickname and avatar; no accounts |
| Scale | One shared lobby, designed for about 10–30 players at a time; teams of 2–5 |
| Teams | Walk to a door, create or join a team, public or password-protected; each team gets its own room instance |
| Puzzle state | Shared per team, so a puzzle solved by anyone is solved for everyone; each player has their own code sandbox |
| Code execution | Pyodide (Python) and sql.js (SQLite), in Web Workers, loaded lazily |
| Validation | Typed answers, Python check expressions and SQL results, all compared against salted hashes |
| Authoring | Each room is a folder with a Tiled map, a JSON manifest and datasets; adding one needs no engine changes |
| Language | German and English throughout |
| Play time | About 30 minutes per room: 5–6 puzzles plus a final lock |
| Starter rooms | Python: "Abandoned research lab". SQL: "Hotel mystery" |

## Steps

Each step ends with typecheck, lint, tests and build passing, and a git commit.

### 1. Scaffold ✅
Vite, React and TypeScript around Phaser 4; event bus between game and UI; DE/EN translations with a key-parity test; lint rule keeping the networking library inside `src/net/`; GitHub Pages deploy workflow.

### 2. Lobby and movement ✅
- Join screen: nickname and avatar choice, remembered in the browser. (Class codes were dropped later in favour of one shared lobby.)
- Lobby map in Tiled format, with placeholder art generated by a script.
- Walking with WASD or the arrow keys, wall collision, and a camera that follows the player.
- Doors defined as Tiled objects. Standing on one shows a prompt; entering rooms comes in step 4.
- Movement keys are ignored while the player is typing in a text field.

### 3. P2P presence and lobby chat ✅
- `Transport` interface plus a Trystero adapter.
- Other players appear in the lobby, with smooth movement and their name labels.
- Lobby chat panel, plus a "nearby" chat channel that only reaches people close by.
- A list of who is online, and handling for players who join and leave.

### 4. Teams and room instances ✅
- Door dialog to create a team or join a team waiting at that door; a team has 1–5 players and a leader who starts the run.
- Each team gets its own room instance, with its own chat channel and shared state.
- Shared state merges without a leader: solved puzzles and revealed hints keep the earliest timestamp per key, and the timer starts at the earliest start time any peer reports.
- Leaving a room returns the player to the lobby; rejoining after a page refresh resumes the run (a reload now lands in the lobby, with a reminder; the player rejoins at the door).

### 5. Room engine and code runners ✅
- Room manifest format with a zod schema and the `validate-rooms` script; rooms are discovered automatically.
- Interactive objects in Tiled (terminals, safes, keypads) open puzzle dialogs.
- Puzzle dialog with a CodeMirror editor and an output panel.
- Pyodide and sql.js Web Workers; a stuck run is stopped by restarting the worker.
- Answer checks (`answer`, `python`, `sql`) and the `hash-answer` script.
- Hints: 1–3 tiered hints per puzzle, revealed for the whole team and counted.
- **Author shortcut:** a developer-only link such as `#/room/sql-hotel?puzzle=3` jumps straight to one puzzle.

### 6. The two starter rooms
- **Quarantine / abandoned research lab (Python):** ✅ content built, playtest pending. Fix a mycologist's broken scripts to collect the 4 override digits: login terminal (variables, `str()`), incubator log (loops, `None`), encrypted notebook (string decoding), sample freezer (dict lookups), ventilation script (debugging), exit keypad.
- **Clues and reveals:** ✅ read-only `clue` objects in maps and manifests, and a puzzle `reveal` shown to the team once solved, so room exploration and coding feed into each other.
- **The Blue Index / hotel mystery (SQL):** ✅ content built, playtest pending. - Each room: about 30 minutes, 5–6 puzzles ordered easy to hard, a final lock combining earlier results, story text in DE and EN, hints, datasets.
- **Debrief screen** ✅ after escaping: what each puzzle practised, model solutions, time and hints used per puzzle; reopenable from the room HUD.
- Playtest each room against the time budget using the author shortcut.

### 7. Proximity, voice/video and collaboration ✅
- ✅ Audio and video connect to players within a radius in the lobby, and to the whole team inside a room.
- ✅ Hysteresis so connections don't flap at the edge of the radius; mute and camera toggles; device selection.
- ✅ When the network blocks it, the game says so clearly and text chat keeps working (as far as the data channel still connects).
- **Nearby ring:** ✅ a faint circle around the local avatar showing who can hear you (for nearby chat and A/V).
- **Speech bubbles:** ✅ nearby chat messages appear briefly above the speaker's head.
- **Private areas:** ✅ zones such as a couch corner or a group of tables, drawn in Tiled as `area` objects. Inside one, "nearby" means everyone in the same area and nobody outside it, whatever the distance. This applies to both nearby chat and A/V. Outside any area, the normal radius applies.
- **Team notebook:** ✅ a shared notes panel in the room, below the team list, where players collect what they find (clue values, digits, suspects, card ids). Anyone can add a note by typing, edit it, drag it to reorder, and cross it off when it's no longer needed; crossed-off notes stay visible but greyed out until deleted. A "pin to notes" button on clue cards and reveals copies their key text in one click. Notes are part of the team's run state and must merge without a leader: each note is keyed by a random id with last-write-wins fields (text, crossed off, deleted) and a sortable position key for the order. They are saved like the run, so a refresh keeps them.
- **Shared code view:** ✅ (watch and copy; real-time co-editing would need a text CRDT such as Yjs) teammates can watch each other's editors live inside a puzzle, so a team can work through a query or script together, as in pair programming.

### 8. Progress, scoreboard, instructor mode, solo mode ✅
- Progress saved in the browser so a refresh restores the run (done in step 4).
- **Rejoin an ongoing run:** ✅ a player who left a room for the lobby can go back into their team's run from the room's door (the saved run is kept until the team escapes or the player discards it).

- **Wrong-attempt counts:** ✅ count failed checks per puzzle, shown to instructors next to hints used, to spot puzzles that are too hard. Counts merge as per-player counters (each player's highest count wins), not as earliest timestamps.
- **Solo practice mode:** ✅ play a room alone without networking ("Practice alone" at a door), for revising at home; not on the scoreboard.

### 10. Time series rooms
Two intermediate rooms that share the classic preprocessing steps (missing-value interpolation, differencing, detrending, log transform, baseline models) but pair them with different model families. Every step is used only where it fits the model:

| Step | TS1: AR/ARMA/ARIMA/SARIMA (statsmodels) | TS2: Prophet-style |
|---|---|---|
| Missing values | Interpolate first: differencing, ACF/PACF and baselines need a complete series | Not needed: Prophet fits on the observed rows and skips gaps; interpolating would invent data |
| Trend | Stochastic trend → difference (`d`, `D` inside the model). Deterministic drift → detrend, then a stationary AR/ARMA. Never both | Modelled by the trend component (with changepoints); no differencing or detrending |
| Log transform | When seasonal swings grow with the level: fit on `log(y)`, back-transform forecasts with `exp` | Same reason; or multiplicative seasonality |
| Differencing | For diagnosis (ADF, ACF/PACF) by hand; in the model only through `d`/`D`, never on already-differenced data | Not used |
| Baselines | Naive and seasonal naive on the same holdout, original scale; a model must beat seasonal naive | Same |

**Infrastructure (before TS1):**
- **Per-room Python packages:** a room manifest lists `packages` (e.g. `["statsmodels"]`); the worker loads them during warm-up. The wheels (about 29 MB: numpy, pandas, scipy, statsmodels and small dependencies) are downloaded by a script, checked against `pyodide-lock.json` hashes, and served from our own site like the Pyodide core. Measured in Pyodide: packages load in about 6.5 s and `import statsmodels` takes about 6 s, so both happen while the dialog opens, not inside the 10 s run limit. A SARIMA fit on 192 monthly points takes under 1 s.
- **Plots in the output panel:** a `show_plot(...)` helper (line charts, ACF/PACF bars) whose data the worker returns alongside stdout; React draws it as SVG. Time series puzzles are hard to solve without seeing the series.
- **Tolerance checks:** forecasts aren't exact, so data files may define a grader function that the `python` check calls (e.g. within ±3 %), returning a fixed result that gets hashed.

**Infrastructure** ✅ (packages, charts, tolerance checks).

**TS1 "Station Nordlys"** ✅ content built (`ts-nordlys`), playtest pending. (Arctic research station; heating fuel, monthly 2010–2025.) A storm put the station into safe mode; to restore heating, the team rebuilds the station's forecasting pipeline and submits next winter's fuel order. Data are generated from an airline model on the log scale (seed chosen so ACF/PACF are textbook-clear; prototype numbers below).
1. **Frost-damaged logbook** (interpolation): four months are missing; fill them with `interpolate(method='time')`. Clue: the logbook page explains the frozen sensor.
2. **Drifting freezer sensor** (detrending + AR): a sample freezer's temperature log has a linear sensor drift. Detrend, fit AR(2), round the coefficients to the keypad code (φ ≈ 0.59 / −0.29 → "6-3"). Differencing instead gives a wrong code. Clue: technician's note "the sensor drifts in a straight line".
3. **The chief's method** (baselines): naive vs seasonal naive MAE on the 2024–25 holdout (≈ 1519 vs 602 litres). Clue: the chief's note "I just order what we used the same month last year".
4. **Stationarity gauge** (log + differencing + ADF; needs 1): show the raw series is non-stationary, then build `log → diff(12) → diff(1)` until the ADF p-value is below 0.05. Clue: the gauge panel.
5. **Echo chamber** (ACF/PACF + AIC; needs 4): read the cut-offs at lags 1 and 12, shortlist candidates, compare AIC on the log training data with `d=1, D=1` inside the model; the airline model (0,1,1)(0,1,1,12) wins.
6. **Supply order** (final; SARIMA forecast + back-transform): fit on the full log series, forecast January 2026, `exp` back, enter it with the freezer PIN. Prototype: log airline MAE 269 beats seasonal naive 602, while the same model without the log only reaches 729.

Model families: AR in station 2, ARMA/ARIMA candidates and SARIMA in stations 5–6.

**TS2 (Prophet):** Prophet can't run in the browser (it needs the Stan C++ toolchain, which Pyodide doesn't ship). Decided: a small Prophet-style model with Prophet's API names, clearly labelled as not the real library. Its scope, what it covers and what not, is in [docs/prophet-lite.md](prophet-lite.md); keep that page in sync. ✅ built as `content/python/prophet.py`, which rooms import through the manifest's `modules`.

**TS2 "Festival Season"** ✅ content built (`ts-festival`, expert), playtest pending. (Festival grounds "Lindenwiese"; daily gate scans 2021 to September 2025.) The office's forecasting server died the week the stages for the Summer Festival 2026 must be ordered. Data are generated in the form of a multiplicative Prophet model (`generate_data.py`): a trend that bends when tram line 7 opens (2023-04-01), yearly and weekly seasonality, two events. Numbers below are from the reference solutions.
1. **Gate scanner log** (Prophet format, missing values): build `df` with `ds`/`y`; the 14 outage days (recorded as 0) and 6 test bookings (exactly 9999) become empty, not interpolated. A threshold like `y > 5000` would also remove real festival days. Clue: IT note.
2. **Tram counter** (changepoints; own dataset, open from the start): with automatic changepoints the largest `delta` sits next to the opening; refit with `changepoints=["2023-04-01"]` and read the trend growth per year before and after (≈ 70 vs 579 passengers a day). Clue: newspaper.
3. **The planner's rule** (baselines; needs 1): holdout June to September 2025; naive 753, last week repeated 422, same day last year (`shift(364)`) 614. Clue: planning notebook.
4. **Lighting desk** (seasonality mode, log; needs 1): holdout MAE additive 516, multiplicative 293, log 433. Clue: whiteboard quick reference.
5. **Events desk** (holidays; needs 1): holidays table from the calendar, with windows (opening Fri to Sun: 0..2; Lantern Night with its rehearsal: -1..0) and 2026 dates; the opening Saturday's effect ≈ +204 % of the trend. Clue: event calendar.
6. **Stage order** (final; needs 2 to 5): multiplicative + holidays + changepoint beats 422 on the holdout (204) and forecasts 19,078 visitors for the 2026 opening weekend (±5 % accepted; automatic changepoints give 19,364). Mistakes land far off: no 2026 dates 10,712, no holidays 12,365, additive 13,345, log 22,141.

Model fit: the Prophet-style model fits by Gauss-Newton with exact non-negative least squares steps instead of L-BFGS, which stalled on the collinear changepoint ramps and gave platform-dependent results; now CPython and Pyodide agree.

## Known limits

- **One shared lobby:** everyone using the site meets in the same lobby, a full P2P mesh. It is meant for about 10–30 people at once; several classes playing at the same time would make it heavy. If that happens, split the lobby again (e.g. a lobby name in the URL) rather than adding a server.

- **Strict networks:** without a TURN relay, voice and video may fail on some school or company networks. Text chat is unaffected.
- **No authority:** with no central server, the scoreboard and the progress the instructor sees can be faked. Instructor messages themselves are signed and can't be.
- **Download size:** Pyodide is about 12 MB, so it is loaded only when a Python puzzle opens. The time series rooms add about 29 MB of packages, loaded only in rooms that declare them and cached by the browser afterwards.

## Ideas not yet scheduled

Add new ideas here before they move into a step.

- **Visual state changes:** a solved object swaps its tile (the freezer opens, the vent fan spins), set via a Tiled property such as `solvedTile`. Best done with the art pass in step 9.
- **Split clues:** some clues show different halves to different players, so the team has to talk. Fits proximity voice.
- **Overlays hide the map:** on smaller windows the chat panel covers the map's lower-left corner, and the camera can't scroll there because the map fits the screen. Either let the camera scroll past the left edge (like `UI_INSET_*`), or make the chat collapsible. Until then, keep important objects out of the lower-left of room maps.
- **Speaking indicator:** highlight the tile (and the avatar on the map) of whoever is talking, using an AudioContext analyser on each remote stream.
- **Italic text in manifests:** RichText only knows `**bold**` and `` `code` ``; a single `*star*` shows literally. Either support it or add a manifest test that rejects it.
- **Clue shortcut for authors:** `#/room/<id>?clue=<id>` to check clue texts without walking.
- **Scoreboard export:** let the instructor export and import the scoreboard as JSON from the panel, as a backup that doesn't depend on returning browsers.
- **Paired t-test station:** a follow-up tasting where the same tasters rate both recipes (`ttest_rel`), next to the independent design of `stats-ab`.
- **Documentation room:** a room that tests reading documentation. The values a puzzle needs are buried in the official docs (a default parameter, a version note, an example's output), and the room only says where to start looking ("the pandas page for `merge`, the section about suffixes"). Needs a way to check answers that doesn't depend on the docs changing: pin the docs version in the links (e.g. pandas `version/2.2/`, `docs.python.org/3.12/`) and pick facts that are stable.
- **Handbook from the HUD:** once a team has found the handbook, a 📖 button in the room HUD could reopen it from anywhere, so nobody has to walk back to the lectern mid-puzzle.
- **Go to from the map:** the instructor's "Go to" menu also on avatar name labels and in the instructor panel's member list.
